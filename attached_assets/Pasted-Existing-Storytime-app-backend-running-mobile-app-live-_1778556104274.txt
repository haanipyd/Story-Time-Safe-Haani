PRIORITY 1 — PAYMENT EVENTS TABLE + WEBHOOK IDEMPOTENCY
══════════════════════════════════════════════════

Add table:

  CREATE TABLE payment_events (
    id BIGSERIAL PRIMARY KEY,
    user_id UUID REFERENCES users(id) ON DELETE SET NULL,
    subscription_id UUID REFERENCES subscriptions(id) ON DELETE SET NULL,
    event_type VARCHAR(50) NOT NULL,
    razorpay_event_id VARCHAR(100) UNIQUE NOT NULL,
    razorpay_payment_id VARCHAR(100),
    razorpay_subscription_id VARCHAR(100),
    amount_paise INTEGER,
    raw_payload JSONB NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    processing_status VARCHAR(20) NOT NULL DEFAULT 'success'
      CHECK (processing_status IN ('success', 'failed', 'skipped_duplicate')),
    error_message TEXT
  );
  CREATE INDEX idx_payment_events_user ON payment_events(user_id);
  CREATE INDEX idx_payment_events_subscription ON payment_events(subscription_id);
  CREATE INDEX idx_payment_events_event_type ON payment_events(event_type);

Update webhook handler `/api/webhooks/razorpay`:

  1. Verify X-Razorpay-Signature using HMAC-SHA256 with RAZORPAY_WEBHOOK_SECRET. Reject 401 if invalid.
  2. Parse event_id from payload.
  3. BEGIN transaction.
  4. INSERT INTO payment_events with razorpay_event_id (relies on UNIQUE constraint).
     • If duplicate key error → log "duplicate_event", update existing row's processing_status='skipped_duplicate', commit, return 200.
  5. If insert succeeds → process subscription state change based on event_type.
     • subscription.activated → update subscriptions.state = 'trial' or 'active', set period dates
     • subscription.charged → state='active', update current_period_end
     • subscription.completed → state='expired'
     • subscription.cancelled → state='cancelled', set cancelled_at
     • payment.failed → log only, no state change (Razorpay retries automatically)
  6. COMMIT transaction.
  7. On any unexpected error: catch, set processing_status='failed', error_message=<stack>, COMMIT (so we don't reprocess), return 200 to Razorpay to prevent retry storm. Alert via Sentry (see Priority 7).
  8. ALWAYS return 200 unless signature invalid.

PRIORITY 3 — DAILY PUSH SENDER SCHEDULED JOB
══════════════════════════════════════════════════

Add new scheduled job: daily_push_sender

Configuration:
  • Runs every hour at :00 (via same cron infra as existing jobs)
  • Enabled via RUN_JOBS=1 (same flag as existing)

Logic per run:
  1. Determine current UTC time. Identify which IANA timezones are at 19:30 (7:30 PM) local right now (give a 60-minute window to catch any).
  2. Query users where:
     • user has at least one active push_token (is_active=TRUE)
     • user has a current_child_id set
     • user has not received the daily push for today (track via a new daily_push_log table OR via a sent_today flag on daily_picks — preferred: add a column to daily_picks called push_sent_at TIMESTAMPTZ)
     • user timezone matches the current 7:30 PM window
       → Need user timezone field. ADD COLUMN: users.timezone VARCHAR(50) NOT NULL DEFAULT 'Asia/Kolkata'
  3. For each matching user:
     • Lookup today's daily_pick for their current child
     • If no daily_pick exists for today, skip
     • Send via FCM to all active push_tokens for the user:
         - title: "Today's story for [Name] is ready 🌙"
         - body: "<story title>"
         - data: { story_id: "<id>", deep_link: "storytime://story/<id>" }
     • Mark daily_picks.push_sent_at = NOW()
  4. Handle FCM token errors: if FCM returns "NotRegistered" or "InvalidRegistration", mark push_token.is_active = FALSE
  5. Log summary: { sent: X, skipped: Y, failed: Z }

Migration:
  ALTER TABLE users ADD COLUMN IF NOT EXISTS timezone VARCHAR(50) NOT NULL DEFAULT 'Asia/Kolkata';
  ALTER TABLE daily_picks ADD COLUMN IF NOT EXISTS push_sent_at TIMESTAMPTZ;
